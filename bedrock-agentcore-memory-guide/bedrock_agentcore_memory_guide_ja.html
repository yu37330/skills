0030秒で理解する

AgentCore Memoryは、エージェントの「今の会話」と「過去から学んだこと」を、別々の仕組みで管理するマネージドサービスです。

短期メモリは「何が起きたか」を残し、長期メモリは「何を覚えるべきか」を抽出・統合する。

最重要ポイントMemoryは正式文書やマスターデータの代わりではありません。ユーザーの文脈、過去の判断、作業の継続性を担当し、正しい根拠はKnowledge Baseや業務DBから取得します。
🗒️

短期メモリ

会話、ツール呼び出し、状態などの生イベント。actorId × sessionIdで整理します。

🧠

長期メモリ

事実、好み、要約、エピソードなどを抽出・統合し、セッションをまたいで検索します。

01経験レベル別の読み方

同じ機能でも、利用者・アプリ開発者・基盤設計者では見るべきポイントが違います。

まず理解

記憶 ≠ ナレッジ

Memoryは「その人・その作業で何があったか」。Knowledge Baseは「正式資料に何と書かれているか」です。

次に理解

短期と長期

短期は会話ログに近く、長期は会話から重要情報だけを抽出したものです。

最後に理解

自動では使われない

保存・検索したメモリを、どのタイミングでプロンプトへ渡すかはアプリ側の設計です。

実装

書き込み

CreateEventまたはSDKのSession Managerで、会話ターンをイベントとして保存します。

検索

Context Hydration

直近イベント、セッション要約、意味検索された長期メモリを組み合わせてモデル入力を作ります。

確認

非同期性

長期メモリ生成には遅延があります。直後の情報は短期メモリから取得する設計が必要です。

設計

Namespace

アクセスパターンとテナント境界から階層を設計し、actor・project・strategyなどを分離します。

精度

Metadata

優先度、工程、設備、期間、状態などを構造化し、意味検索の前に候補を絞ります。

最適化

Custom Strategy

業務固有の抽出・統合ルールが必要な場合はBuilt-in OverrideまたはSelf-managedへ進みます。

02AgentCore Memoryは何を解決するのか

LLM自体は、API呼び出しが終わると以前の会話を覚えていません。アプリケーションが文脈を保存・選択・再投入する必要があります。

🔁

繰り返し説明

ユーザーが毎回、目的・好み・過去の判断・作業状況を説明し直す。

📚

コンテキスト肥大

会話履歴を全件プロンプトへ詰め込み、コスト・遅延・ノイズが増える。

🧩

学習の分断

別セッションや別エージェントへ、過去の経験や判断が引き継がれない。

AgentCore Memoryの価値生の履歴を保存するだけでなく、重要情報の抽出・既存情報との統合・意味検索までを、短期メモリと長期メモリとして分離して提供します。

03全体の仕組み

「保存」と「思い出す」は別処理です。さらに長期メモリの生成は非同期で動きます。

設計上の注意イベントを書いた直後に、同じ内容が長期メモリで検索できるとは限りません。最新のターンは短期メモリ、過去の知見は長期メモリから取る「二段構え」が基本です。

04基本用語を一気に整理

用語意味設計時の問い工程分析の例
Memory Resourceイベントと抽出済みメモリを保持する最上位コンテナ。アプリ、業務、環境のどの単位で分けるか。工程分析エージェント用Memory。
Actorエージェントとやり取りする人・他エージェント・システム。誰の記憶として保存するか。分析者ID、設備ID、チームID。
Session一連の連続した対話・作業。sessionIdでイベントを束ねる。どこで作業を区切るか。不良ロットAの原因分析セッション。
Event短期メモリの最小単位。会話、ツール実行、状態など。何を証跡として保存するか。SQL、グラフ生成、仮説の採否。
Memory Strategy生イベントから何を抽出・統合するかを決める規則。何を長期間覚える価値があるか。有効だった分析手順や判断条件。
Memory Record長期メモリの構造化された記録単位。検索結果をどう評価・利用するか。「設備温度上昇後に欠陥率増加」。
Namespace長期メモリを論理的に分離する階層パス。誰・何・どの範囲で隔離するか。/plant/A/process/P10/actor/123/
Metadata検索を絞り込む構造化属性。意味の近さ以外に何で選別するか。工程、設備、品番、重要度、期間。

05現在の4つの組み込み戦略

2026年8月時点の公式ドキュメントでは4種類です。2025年の初期ブログにある「3種類」という記述は、Episodic追加前の情報として読む必要があります。

Semantic

事実・文脈

会話から重要な事実やエンティティ、期限、識別子などを抽出します。

向く例：案件番号、分析対象、決定事項、バージョン。

User Preference

好み・スタイル

ユーザーが好む形式、選択、作業スタイルを蓄積します。

向く例：グラフ形式、粒度、報告書の書き方。

Session Summary

会話要約

長い一つのセッションを、主要トピック・判断・進捗に圧縮します。

向く例：原因分析の途中経過、未解決事項。

Episodic

経験・振り返り

一連の出来事をエピソードとして構造化し、複数経験からReflectionを生成します。

向く例：トラブル対応手順、成功・失敗パターン。

どの戦略を選ぶか

覚えたいもの第一候補補助候補注意点
ユーザーや案件に関する明示的な事実SemanticSummary正式なマスタ値は業務DBを正本にする。
表示形式や分析スタイルUser PreferenceSemantic推定した好みは確信度と更新条件を意識する。
長い作業の途中経過Session SummarySemantic最新ターンは短期メモリから補う。
過去の一連の対応とそこからの教訓EpisodicSemantic成功条件・失敗条件を評価データで検証する。
業務固有の厳密な項目Built-in OverrideSelf-managed抽出スキーマ、監査、再現性を設計する。
実装自由度は3段階①Built-in：最短で開始、②Built-in with overrides：プロンプトや利用モデルを調整、③Self-managed：抽出・統合・スキーマ・外部DB連携まで自分で制御。

06Knowledge Base・DB・ログとの使い分け

「何でもMemoryへ入れる」は失敗しやすい設計です。情報の役割ごとに正本を分けます。

保存先答える問い適した情報工程分析での例
AgentCore Memory誰が、過去に何をし、何を学んだか。会話文脈、好み、過去判断、作業経過、経験。前回の仮説、よく使う分析軸、未完了タスク。
Bedrock Knowledge Base正式な資料には現在何と書かれているか。規程、設計書、FMEA、手順書、報告書。管理基準、設備仕様、標準作業、過去トラブル。
業務DB / Lakehouse現在の正確な値・状態は何か。構造化データ、トランザクション、時系列、マスタ。測定値、不良率、設備条件、ロット・品番。
Object Storage原文・成果物・大型データはどこか。生ファイル、画像、CSV、モデル成果物。波形、画像、分析Notebook、レポート。
Observability / Audit Logシステムがいつ何を実行したか。トレース、エラー、コスト、レイテンシ、監査。どのツール・SQL・モデルが回答を作ったか。
Memoryを正本にしてはいけない代表例設備の現在状態、最新の工程条件、承認済み仕様、法規・品質規程、権限判断、金額や在庫などのトランザクション情報。

07検索・Namespace・Metadata設計

精度を決めるのは「保存量」よりも「検索範囲と選別方法」です。

Namespace = 誰・何を分けるか

ファイルパスのような階層で、長期メモリの論理境界を作ります。先に検索パターンを考え、後から階層を決めます。

/org/{orgId}/plant/{plantId}/
  process/{processId}/actor/{actorId}/
    semantic/
    preferences/
    episodes/

代表的な変数：{actorId}、{sessionId}、{memoryStrategyId}

Metadata = 同じ範囲の中で絞る

Namespace内で意味検索する前に、業務属性で候補を絞ります。特に履歴が増えた後のノイズ抑制に有効です。

{
  "process_id": "P10",
  "equipment_id": "EQ-204",
  "product_family": "A12",
  "priority": "high",
  "status": "validated",
  "analysis_type": "root_cause"
}

現在の公式仕様では、長期メモリ検索で複数のフィルターをAND条件で利用できます。

検索時のおすすめ順序

1. Identityactor・tenant・権限を確定
→
2. Namespace検索可能な論理範囲を限定
→
3. Metadata工程・設備・期間・状態で絞る
→
4. Semantic質問との意味的な関連度で順位付け
→
5. Rerank / Policy鮮度・信頼度・利用可否を最終判定
設計のコツNamespaceは「主たる隔離境界」、Metadataは「隔離された範囲内の業務フィルター」と考えると整理しやすくなります。

08最小実装の流れ

最初はSemantic戦略一つで、保存 → 抽出待ち → 検索 → プロンプト注入のループを動かします。

① Memory作成戦略、保持期間、暗号化、Namespaceを設定
→
② Session作成actorIdとsessionIdを決定
→
③ Event保存USER / ASSISTANT / TOOL等の会話ターン
→
④ 長期化Strategyが非同期で抽出・統合
→
⑤ RetrieveNamespace・Metadata・意味検索
→
⑥ Context注入回答生成後、新イベントを保存

概念を掴むための最小コード例

from bedrock_agentcore.memory import MemorySessionManager
from bedrock_agentcore.memory.constants import ConversationalMessage, MessageRole

# 1. 作成済みMemoryへ接続
manager = MemorySessionManager(
    memory_id="YOUR_MEMORY_ID",
    region_name="us-west-2",
)

# 2. 誰の、どの作業かを明示
session = manager.create_memory_session(
    actor_id="analyst-123",
    session_id="lot-A-root-cause-20260806",
)

# 3. 会話を短期メモリへ保存
session.add_turns(messages=[
    ConversationalMessage(
        "設備EQ-204の温度上昇と欠陥率の関係を確認したい",
        MessageRole.USER,
    )
])

# 4. 直近文脈は短期メモリから取得
recent_turns = session.get_last_k_turns(k=10)

# 5. 長期メモリは別途、関連する記録を意味検索して
#    Knowledge Baseや業務DBの結果と一緒にLLMへ渡す

SDK・CLIは更新されるため、実装時は公式Getting Startedと公式Samplesの現行コードを確認してください。

Phase 1：PoC

Semanticのみ。1ユーザー・1ユースケース。手動で検索結果を確認。

Phase 2：業務試行

SummaryやMetadataを追加。KB・DBと統合し、回答根拠を表示。

Phase 3：本番

Namespace分離、IAM、KMS、監査、評価、削除・訂正フローを実装。

09工程分析エージェントへの適用

薄いオントロジーと組み合わせる場合、Memoryは「分析の継続性」、KBは「正式知識」、データ基盤は「事実」、オントロジーは「最低限の関係」を担当します。

工程分析で「覚えるもの」と「覚えないもの」

Memoryへ覚えさせる

分析テーマ採用・棄却した仮説有効だった分析手順次に確認する項目利用者の表示嗜好過去の対応結果

正本へ問い合わせる

最新の測定値承認済み工程条件設備マスタ品質判定正式な原因分類権限・機密区分

薄いオントロジーとの相性最初から完全な原因体系を作らず、工程・設備・条件・現象・原因候補・対策の6概念程度を共通語彙として持ち、具体的な分析経験はEpisodic Memoryへ蓄積する構成が現実的です。

10本番運用で外せない設計

🔐

隔離と権限

tenant・actor・projectの境界をNamespaceとIAMで一致させます。別ユーザーのメモリ混入は重大事故です。

🧽

訂正・削除

間違った記憶を修正・削除できる管理画面と運用フローを用意します。会話の訂正だけでは不十分です。

⏱️

鮮度

非同期生成の遅延、古い記憶の優先度、情報が変わった時の統合ルールを評価します。

🧪

評価

抽出精度だけでなく、検索結果が最終回答を改善したか、誤誘導しなかったかを測ります。

💰

コスト

全ターン保存・全戦略適用・毎回大量検索を避け、価値のあるイベントと検索タイミングを選びます。

🔭

Observability

何を保存し、何を検索し、どの記憶が回答に使われたかをトレース可能にします。

よくある失敗

失敗なぜ起きるか改善策
会話を保存しただけで「記憶できた」と考える長期戦略を設定していない、または検索・注入していない。Write・Extract・Retrieve・Useの4段階を監視する。
全履歴を毎回モデルへ渡す検索設計がなく、履歴が増えるほどノイズ化。直近ターン＋要約＋関連長期メモリへ分割。
Namespaceを後付けするテナント混入や取得範囲の肥大化が起きる。アクセスパターンと権限境界から先に決める。
Memoryだけで回答する記憶は最新・正式・完全とは限らない。KB・業務DBを正本にし、Memoryは補助文脈に限定。
保存量だけをKPIにする低品質な記憶が増え、誤検索やコストを増やす。利用率、正確性、回答改善率、誤誘導率で評価。

11評価方法：Memoryが本当に役立ったか

「保存できた」ではなく、「必要な記憶を正しく取り出し、回答や作業を改善したか」を測ります。

Extraction

Precision / Recall
覚えるべき情報を正しく抽出し、不要情報を残さないか。

Consolidation

重複・矛盾率
同じ内容を増殖させず、新旧情報を正しく更新できるか。

Retrieval

Recall@K / MRR
質問に必要なメモリが上位に返るか。別ユーザー情報が混ざらないか。

Task Impact

成功率・時間・再質問数
Memoryありで最終タスクの品質が実際に上がるか。
