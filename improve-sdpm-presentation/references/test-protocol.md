# 比較テスト手順

## 固定条件

- 同じ原稿、Brief、Outline、ページ数、主要メッセージを使う。
- AをSDPM単体、BをSDPMと改善Skillの組み合わせとする。
- AとBを同じ解像度で全ページPNG化する。
- 自動レビュアーには期待結果やファイル名の優劣を渡さない。
- Windowsで文字コードエラーが出る場合はUTF-8実行を明示する。
- 標準レンダラーを使えない場合はPowerPointまたはLibreOfficeで同一解像度へ書き出し、方式を記録する。
- 実行時間、ツール呼出し回数、入出力トークンを記録する。

## 3方式の比較

- A: 従来SDPMで初稿を作成
- B: 従来SDPM初稿を生成後に改善
- C: Deck Plan v3＋Design Direction Scout＋Visual Plan v8＋Design Systemを使ってSDPM初稿を作成し、Review Issueだけ差分修正

CがBと同等以上の品質で、生成時間とトークンを削減できるかを本番化の中心指標とする。

## 自動評価

1. A/B/Cの識別子をランダム化し、`$review-presentation-visuals` version 8で独立に評価する。
2. 3秒理解、意味と図解の適合、意味上の図解反復、完成画像の視覚文法、反復モチーフ、サムネイル類似クラスを明示的に検査する。
3. 9点以上には、同種の実務資料と比べて優れている観察事実を要求する。
4. 軸ごとの根拠と留保を残し、Issueが0件でも改善余地を省略しない。

## 人間によるブラインド評価

- ファイル名と生成方法を隠し、表示順を入れ替える。
- 3秒だけ表示し、「何を伝えるページか」を回答してもらう。
- 読みやすさ、信頼感、図解の納得感、好みを各5段階で記録する。
- 軽微な文言・図形修正を依頼し、完了までの手直し時間を測る。
- 可能なら3名以上、最低でも対象読者に近い1名で行う。

## 合格条件

- Bの自動評価がAより10点以上高い。
- Bの全評価軸が7以上で、`critical`と`major`が0件である。
- Bの視覚文法テストが合格し、箱優位率・結論帯率・空間構成数・主役図形数が改善している。
- 同じモチーフ共有率、ノード＋線主役率、最大高類似クラス比率が上限内である。
- 内容・ページ数・発表者ノートの欠落や無断追加がない。
- 人間評価でBがAを上回り、手直し時間が短い。
- 別題材でも同じ改善傾向を再現する。
- Cの初稿Review v8が80点以上かつDesign Direction、Locked Layout、Anti-Slop、Design System監査・機械証跡・納品ハードゲートを満たす。
- Evidence ID実照合、PPTX内容Diff、日本語Lint、4辺QAがpassする。
- Cの最終品質がB以上で、AまたはBに対して実行時間と総トークンを40%以上削減することを目標にする。
- 既知欠陥入りテストで、タイトル切れ、必須タグ欠落、出典切れ、重なりを誤合格させない。

人間評価または別題材テストが未実施なら、`automated_visual_pass: true`でも`poc_status: pending_human_validation`とする。

## ループ

失敗軸をVisual Plan、Design Token、Renderer選択、レビュー基準のいずれかへ関連付ける。個別ページ専用の例外を増やさず、別題材でも有効な規則だけをSkillへ戻す。
